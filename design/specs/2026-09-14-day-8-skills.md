# Day 8 — The agent skills, `/analyze`, and the decision-log route

**Status:** in implementation. Sections 2, 3 and 7 were rewritten partway through, after
per-task review found thirteen defects that changed what the toolbox routes do. Section
7.1 records the pattern.
**Extends:** `design/specs/2026-09-13-day-7-contracts.md`, which left the skills unwritten.

## Why this exists

Day 7's brief was "contract repairs, then the five skills". The contracts consumed the
day, and `skills/` and `commands/` are both still empty. Day 8 therefore carries the
whole second half of day 7 as well as the report work the schedule assigned it, which is
more than one day holds. This spec covers four skills, the `/analyze` command, and the
toolbox routes they need. `write-report`, the report template and the first dataset-1
run are named in section 6 and handed on.

The skills are prose the agent reads *at runtime* to make decisions, which is why
`CONTEXT.md` was pulled forward to day 6: a glossary written after the skills would
document whatever vocabulary they had drifted into rather than governing it. Everything
below is written in its terms, and section 4 names what it still lacks.

## 1. Control flow and resumption

`/analyze` holds the sequence. Each skill does one stage against `--run-dir` and
returns, knowing nothing about its neighbours.

```
/analyze <dataset> [--run-dir R] [--auto] [--budget fast|standard|thorough]

  0.  drtools status --run-dir R          <- only when --run-dir was given
  1.  profile; recon                       (Skill: profile-dataset)
  2.  checkpoint                           unless --auto
  3.  Plan, then register                  (Skill: plan-analysis)
  4.  prepare-reference; embed each        (Skill: execute-plan)
  5.  evaluate each; rank; figures         (Skill: evaluate-embeddings)
  6.  re-plan round, at most once          -> 3, 4, 5   [optional]
  7.  report                               (Skill: write-report — section 6)
```

Step 0 runs only when `--run-dir` names an existing Run; a fresh invocation has nothing
to ask about and goes straight to step 1, where `profile` creates the Run. Resuming is
therefore `/analyze <dataset> --run-dir runs/<id>`, and the two paths differ by one
command rather than by two modes.

On day 8, step 7 does not exist. `/analyze` ends after step 6 by printing where the Run
directory is and saying that the report stage is not yet built — an explicit stop rather
than a silent one, so the missing stage cannot be mistaken for a finished analysis.

**Why the command orchestrates rather than the skills chaining.** `design/notes.md` §1
fixes five skills, one `/analyze`, and no subagents; it does not say where the sequence
lives, and line 22 reads either way. Putting it in the command keeps every skill
individually runnable — which day 8's end-to-end drive depends on, and which makes a
single stage debuggable without replaying the four before it. It also keeps the re-plan
loop in one place: distributed hand-offs would make the graph cyclic across five files.

**Resumption is a toolbox route, not prose.** `/analyze`'s first act is
`drtools status --run-dir R`, which reports stage by stage what the Run holds. It enters
at the first incomplete stage. The alternative is prose telling the agent which files to
stat, which decays silently and cannot be tested. `status` makes §2.2's "the Run
directory is the only state" something the agent can *ask* rather than something it must
remember to check.

**The re-plan round** may only add Candidate ids or revise Candidates that failed, timed
out or crashed. This is narrower than §3.1 imagined, and the narrowing is day 7's doing:
`_check_reregistration` refuses any move to the Pre-registered weighting or the Base
preprocessing. Section 6 records the consequence. The round is entered only when
evaluation gives a reason, and the reason is logged either way, so "the agent considered
a second round and declined" is on the record as much as "the agent added `c6`".

`status` derives whether the round is spent from the decision log rather than from
files, following day 7: the log is append-only and predates every Embedding, so it is
the authority and the file is not.

**The checkpoint belongs to `/analyze`.** A skill that sometimes asks the user and
sometimes does not is a skill with a mode. Keeping the checkpoint in the command leaves
all four skills unconditionally non-interactive, which is what lets them be run alone.
Per §5 it is at most one or two multiple-choice questions, each stating a default, never
blocking; `--auto` suppresses it, and the two graded runs use `--auto`.

## 2. New toolbox surface

Three added routes, plus four changes to existing commands that the adversarial review
in section 7 forced: `Plan.budget` gains a consumer and a freeze, `embed --timeout`
becomes a cap, `embed` refuses a third attempt on one Candidate, and the adapter's
digest is recorded. No new Budget argument is added — see below for why the draft's was
wrong.

### `drtools status --run-dir R`

Read-only. Reports each stage's state: whether the Run has been profiled and
reconnoitred, whether a Plan is registered, which Candidates have an Outcome, which of
those have metrics, whether a ranking exists, whether the re-plan round is spent, and
the Run's seed and Budget. Existence comes from artefacts; anything the freeze governs
comes from the decision log.

Per Candidate it reports `outcome`, `attempts`, `retry_available`, `abandoned` and
whether it has metrics. It also reports `next`, the first stage with work outstanding.

No side effects, so `/analyze` may call it freely and a human may use it to find out
what a half-finished Run holds. *Read-only means read-only*: it opens the Run without
constructing its subdirectories, because a command that only reports must not modify
what it reports on.

**Five derivations are harder than they look**, and every one was got wrong before it
was got right. They are recorded because the skills depend on them and because in each
case a simpler rule is silently incorrect rather than obviously so.

*`attempts` counts `embed` records.* `_recorded_outcome` already reads that log but
returns only the last outcome, so the count is derivable today and derived nowhere.
Without it the one-retry rule is a claim about conversation history rather than about
the Run. An attempt counts when it *ends*, not when it begins: one killed with the
parent process gets its allowance back, which is the reading an interrupted Run already
receives — recoverable rather than wedged.

*`retry_available` is not "has no Outcome".* A Candidate that failed *has* an Outcome,
so reading existence alone would skip it on resumption, making a failure permanent
because a process died rather than because the diagnosis was exhausted.

*`abandoned` exists because a retry need not reuse the failed id.* The sanctioned repair
is often a differently-shaped attempt under a new id, leaving the old Candidate failed
for the record. Counting attempts alone, that Candidate would offer a retry nobody
intends to take and the Run would route to `execute` for ever. Giving up is therefore
*recorded* through `log-decision`, not inferred.

*`ranked` is not "`ranking.json` exists".* Nothing clears the ranking when the portfolio
changes — `_invalidate_candidate` clears only a Candidate's own artefacts — so a
re-plan round would leave a stale ranking that ends the Run early. `rank` stamps the
ranking with the digest of the Plan it ranked, so the question is asked directly.

*`replan_round_spent` is the subtlest*, and three plausible definitions are each wrong.
Counting registrations is wrong: re-registering an identical Plan is legal and appends a
record, so merely revalidating would consume the round. Comparing Plan digests is wrong:
revising a failed Candidate is the ordinary retry and changes the digest. Anchoring on a
ranking is wrong: ranking needs metrics from a Candidate that succeeded, so a Run where
everything failed would never record one and would be offered the round for ever. The
round is a registration that **adds Candidate ids, net of those abandoned since the
previous registration**, once something has been attempted. Replacing is retrying;
growth beyond replacement is the round.

**`next` must never name a stage that cannot complete.** Two cases force this. A Run
with a registered Plan is never sent back to `recon` — `validate-plan` accepts a Plan
without reconnaissance, and naming it would invite re-tuning the evidence the Plan was
argued from, which is the `recon --k` hole day 9 owns. And a Run where every Candidate
failed is never sent to `evaluate`, because `rank` raises without successful metrics; it
takes the re-plan round if unspent and reports otherwise, since every Candidate failing
is a finding rather than an error to loop on.

### `drtools log-decision --run-dir R --json @path`

The Locked-core route to `decisions.jsonl`. A JSON document rather than flags, matching
the `@path` convention `--plan` already uses: rationales are prose that will contain
quotes, and shell quoting is where that goes wrong.

It **refuses** a decision whose `evidence` holds a key that resolves to `MISSING`,
naming the key, the artefact it looked in, and the keys that do exist at that level. It
**accepts** an empty `evidence` list, which renders as unsupported in the report. That
is day 2's distinction held to: a legitimately absent measurement is a finding, a
citation pointing at nothing is a broken rationale, and collapsing the two would hide
the exact failure the mechanism exists to catch.

It also **stores what each key resolved to at the moment the decision was made**, as
`evidence_resolved`. Validation already calls `resolve_evidence`; this keeps the result
instead of discarding it.

That second part is not tidiness. Artefacts are rewritten in place — `recon` still
carries its own `--k`, which day 9 owns — so a key that resolved to one value when the
decision was logged can resolve to another by the time the report reads it, silently
rebinding a rationale to evidence that was never behind it. Checking a key at write time
and reading a value at report time are not the same guarantee unless the log carries the
value it saw. Storing it makes the decision log self-contained about what was read, and
makes divergence detectable rather than invisible.

Detecting that divergence belongs to the report generator, which is day 8b, because that
is where evidence is read back. Day 8's obligation is to record enough that day 8b
*can*.

This makes citation integrity enforced rather than advertised, which is what the day 6
adversarial pass found it was not. It still does not make a rationale *true*: a real key
with a false reading passes. The notes must keep saying so, and the report must not
imply otherwise.

#### The route must not be able to forge what the freeze reads

This was not in the first draft of this spec and it should have been. Opening a general
write route into `decisions.jsonl` is not a neutral convenience, because day 7 made that
log the authority: `rank` cross-checks registration against it, attempts are counted from
it, and `status` derives the entire state machine from it. All of that holds only while
those records come from the command that performed the step.

As first written, `log-decision` accepted any `stage` and any extra field. A caller could
append a `register_plan` record carrying a fabricated `plan_digest` and satisfy
`_check_registration_is_recorded` without ever validating a Plan — the pre-registration
guarantee defeated by the mechanism built to record it. It could equally spend a
Candidate's attempts without running it, or assert a ranking it never computed.

So the route **refuses two things**:

- the lifecycle stages `recon`, `embed`, `rank`, `validate_plan` and `register_plan`,
  naming the command that produces the real record;
- the fields the freeze reads off those records — `plan_digest`, `outcome`, `weights`,
  `candidates`.

The agent's own stages — `profile`, `plan`, `execute`, `evaluate` — are unrestricted, and
so is `candidate` in the singular, which is what carries `abandoned`. The line is not
between the agent's judgments and the toolbox's: the agent may record any judgment it
likes, including giving up on a Candidate. It is between *describing a decision* and
*asserting that a step was performed*.

Worth stating as a general rule, because it will come up again: **anything that reads the
decision log as evidence of an event must be unwritable through any route the agent
controls.** Day 7 established the log as the authority; day 8 nearly gave away the pen.

### `drtools suggest-base --run-dir R`

Returns a suggested Base preprocessing Stage list with its rationale and Evidence keys,
derived from the same published rule `recon` uses to choose its Probe representation.
The planner accepts it or overrides it with a logged reason.

This implements the connection day 6 identified and deferred: both the Probe
representation and Base preprocessing answer "what transform makes distances on this
data meaningful", by different mechanisms. The payload says in as many words that it is
a suggestion crossing a boundary, not an identification — day 6 decided deliberately
that the two are different things and that collapsing them would be the wrong fix. One
implementation of the rule, not a prose copy that drifts.

### Budget: give the existing field a consumer, and make the cap a cap

An earlier draft of this spec proposed `--budget` as a new run-level immutable on the
manifest, alongside `--seed`. That was wrong, and checking rather than assuming is what
found it. **`Plan.budget` already exists** at `plan.py:88`, typed
`fast|standard|thorough` and defaulting to `standard`. It has **no consumer anywhere in
the toolbox** — a declared field nothing reads — and `_check_reregistration` does not
freeze it. Adding a second Budget would have given the Run two authorities that nothing
required to agree, which is the same shape of defect as the day 6 review's
profile-against-cache divergence.

So day 8 adds no Budget of its own. Instead:

- **`Plan.budget` is the single authority.** `/analyze --budget` reaches the toolbox by
  being written into the Plan the agent registers, which means it passes through the
  existing registration event and needs no new immutability machinery.
- **`_check_reregistration` freezes it**, alongside the weighting and the Base
  preprocessing. A Budget that can be raised after a Candidate has timed out is not a
  constraint the agent allocated under, and the report would describe a resource
  discipline the Run did not keep.
- **`embed --timeout` becomes a cap, not a default.** A default is advisory — any caller
  may pass a larger value and the Run silently exceeds the Budget it declared. `embed`
  derives the maximum from the registered Plan's Budget and refuses a `--timeout` above
  it, naming the Budget and the cap.

This keeps §4's claim honest. The Budget is a resource the agent allocates, and it can
only be that if it reaches the commands that spend it and binds them when it arrives.

**The `--in-process` bypass.** `embed --in-process` skips subprocess isolation entirely,
so it has no wall-clock cap at all and no Budget can bind it. It exists because the
tests need it — seven test modules use it — and it is a developer affordance that the
agent has no reason to touch. Prose saying "the skills do not use it" is not enforcement,
which is the lesson day 7 already paid for. The proposal is to gate it behind an
environment variable the test harness sets, so the flag stays available where it is
needed and is unreachable from a skill.

That gate is roughly five lines and it is a judgment call rather than a necessity —
flagged here so it can be cut without unpicking anything else. Cutting it means the
Budget is enforced on every route the agent actually uses and bypassable on one it has
no reason to use, which is weaker than it sounds only if a skill is written carelessly.

### What deliberately does not change

`recon` keeps its own `--k` and `--max-samples`, so the agent can still tune the
evidence that justifies its own Plan. That is a real hole; day 7 assigned it to day 9,
and widening day 8 to cover it is how a one-day slip becomes two. The skills will not
use those flags, but prose is not enforcement, and this gap is known and owned
elsewhere.

## 3. The four skills

### Shape

Every skill takes the same form, decided deliberately:

- **Steps** — the toolbox calls and their order, as exact numbered commands. A skipped
  call is then visible in the decision log and in `status`.
- **What to attend to** — what the measurements imply, briefed rather than tabulated.
- **Traps** — the known ways this stage goes wrong, each phrased as what to check.
- **What to log** — which decisions this stage must record, and which Evidence keys are
  available to cite.

The command sequence is fixed and the judgment is open. Prescribing the judgment too
would rebuild the lookup table §3.1 rejected, in prose instead of code; leaving the
sequence open would mean nothing guarantees `evaluate` runs before `rank`, and the Run
artefacts are the deliverable. `writing-for-agents` governs how the files themselves are
written.

Each skill's first step reads state from the Run, never from the conversation. Because
there are no subagents, the whole chain runs in one context and the agent *will* have
seen the earlier stages — so §2.2's rule is a discipline the prose enforces, not
something the runtime enforces for us. That is worth stating because it is the
assumption most likely to be quietly violated.

### `profile-dataset`

Runs `profile` then `recon`, reads the `observations` from both, looks at the
reconnaissance thumbnail as an image, and logs what the measurements imply.

The Open adapter lives here. When no built-in Loader recognises the input, the skill
writes `load(path) -> (X, labels, meta)` into the Run directory as `adapter.py` — inside
the Run, so the Run stays self-contained and the adapter is part of the record — and
passes it with `--adapter`. The Loader contract checks the returned data before anything
downstream runs. The adapter decision is logged, including what the built-in Loaders
refused and why.

**What the Loader contract does not check, said plainly.** `_load_via_adapter` calls
`exec_module` at `loaders/__init__.py:197`, so adapter code runs in the toolbox process,
with the user's permissions, *before* any contract check. The contract governs the
matrix that comes back; it cannot govern what the module did on the way. The module's
own docstring currently says "An agent-written adapter is therefore no more trusted than
a built-in loader", which is true of the data and false of the execution, and reads as
the stronger claim. **That sentence gets narrowed** — this is §2.3's lesson again: the
overstatement is in the prose, and the fix is to describe the mechanism accurately.

Day 8 adds the auditable half:

- **The adapter's content digest** is recorded in `meta` and on the manifest, so the
  Run's record names exactly which code produced the matrix. Today `meta` carries only
  the adapter's path, and a path is not a version.

Day 8 does **not** sandbox adapter execution, and the reason is worth stating rather
than leaving as an omission. The threat model here is a grader running this agent in
Claude Code on their own machine, where the agent already has shell access with the same
permissions. A filesystem-and-network policy around the Loader, sitting underneath a
runtime that has no such policy, would not contain anything an adapter could otherwise
do — but it would let the report claim a containment property the system does not have.
That is precisely the class of overstatement the day 6 pass punished in §2.3, and the
right response is the same one: claim what is true.

What *is* worth building is running the adapter through the existing subprocess
isolation, which would give it a wall-clock cap and killability and would keep a runaway
or hanging adapter from taking the toolbox down — the same argument §4 already makes for
Candidates. It is not free: `isolation.py` is shaped around a Candidate producing an
Embedding, and returning a possibly-sparse matrix across a process boundary is real
work. **Day 9**, where the queued Loader defects already are, rather than claimed for
day 8 on an estimate that has not been made.

Traps to carry: an intrinsic dimension near the ambient dimension is not evidence of
nothing until graph connectivity has been checked; the Probe representation means every
reconnaissance number is conditional on a transform, and the skill must say which; a
Loader that refuses missing values is refusing on purpose, and imputation is a decision
to log, not a default to reach for.

### `plan-analysis`

Reads `profile.json` and `recon.json`, consults `drtools methods` for Capability
records, takes `suggest-base` and `suggest-params` as audited starting points, composes
the Plan, and submits it to `validate-plan` — which is the registration event. On
refusal it revises from the message and resubmits; **every refusal is logged**, which is
what lets the report say "the planner proposed X, the validator caught it, the agent
revised to Y".

The Plan must carry 3–5 Candidates spanning families with a plain-PCA Candidate always
present, every Rejection recorded with its reason and Evidence keys, and the
Pre-registered weighting with its justification.

The weighting is the one irreversible choice in the Run. The skill must say so plainly:
once `validate-plan` registers, the weighting cannot move, Amendment has no mechanism,
and a changed weighting means a new Run.

**Second-round mode.** When `status` reports a Plan already registered, the same skill
runs in a narrower mode: it may add Candidate ids and revise failed ones, and nothing
else. §3.5's hyperparameter sweep on the top-ranked Candidate is exactly this case, so
the sweep and the re-plan are one mechanism rather than two.

### `execute-plan`

Runs `prepare-reference` once, then `embed` for every Candidate that `status` reports as
having no Outcome **or** a non-`ok` Outcome with `retry_available` still true. On a
failure, timeout or crash it reads the structured record — exception class, message,
Stage, parameters — diagnoses, and takes **one** retry: revise the failed Candidate's
Stages or register a new id, re-register, re-embed. After one retry it records a
permanent failure and continues with the rest.

**The retry has to be Run state, not conversation state.** An earlier draft said "per
Candidate that lacks an Outcome", which is wrong in both directions. A Candidate that
failed *has* an Outcome, so resuming after an interruption would skip it and the
promised retry would be lost — the failure becoming permanent because the process died,
not because the diagnosis was exhausted. In the other direction, nothing counts
attempts: `_check_reregistration` permits revising a failed Candidate any number of
times, so repeated invocation can retry without limit while the design claims one.

Both are closed by the same mechanism. `status` reports `attempts` and
`retry_available`, counted from the decision log, and **`embed` refuses a third attempt
on the same Candidate id**, naming the two attempts and pointing at registering a new id
instead. The rule then holds regardless of how the Run was interrupted or how many
times a command was invoked, which is what "the Run directory is the only state" is
supposed to mean.

**Registration is a toolbox event, not a skill's property.** `execute-plan` calls
`validate-plan` itself to re-register a retry revision; it does not hand back to
`plan-analysis` to do it. The freeze governs what any caller may change, so nothing is
gained by routing the call through a different skill, and conflating the per-Candidate
retry with the once-per-Run re-plan round would destroy a distinction the design needs:
the retry is one per method and immediate, the round is one per Run and happens after
evaluation.

The diagnosis is the judgment, and it is where the most convincing evidence of agency in
the whole system comes from. The skill briefs the known repairs rather than tabulating
them: a disconnected neighbourhood graph wants more neighbours, a `MemoryError` wants a
subsample Stage ahead of the method, a timeout wants either a smaller problem or an
acknowledgement that the method does not fit this Budget.

**Giving up is an act, not an absence.** When the allowance is spent, or when the repair
is a replacement Candidate under a new id rather than a revision of the failed one, the
skill records that it has given up on the original — through `log-decision`, with
`candidate` and `abandoned`. `status` reads it, and without it the Run keeps offering a
retry nobody intends to take and never leaves `execute`. It also keeps the two
allowances apart: a replacement is the Candidate's one retry, and it must not silently
consume the Run's one re-plan round.

Traps: a Candidate that already succeeded is frozen, and a variant needs a new id; a
Candidate that subsampled below what the registered `k` supports will be refused at
evaluation, so the subsample is a planning-time constraint, not an execution-time one;
`--timeout` above the registered Budget's cap is refused, so a timeout is not escaped by
asking for more time.

### `evaluate-embeddings`

Runs `evaluate` per Candidate with an Outcome of `ok`, then `rank`, then `figures`, then
*looks at the figures*. Day 6 established that rendering and looking catches what tests
of the plotting code do not — both figure bugs that day were found that way, and the
second was introduced by the fix for the first.

It then logs its reading of the ranking and, explicitly, whether a re-plan round is
warranted and why — recorded either way.

Traps, all of them measured rather than assumed: t-SNE cluster sizes and inter-cluster
distances are not meaningful and must not be interpreted; a Reference value is a
baseline and not a ceiling, and an Embedding exceeding it is a real phenomenon rather
than an error, because distances concentrate in high dimensions and discarding noisy
directions can recover structure the full space obscured; a metric dropped for being
unavailable on some Candidates changes what the weighting means, and `rank` says so and
says by how much.

## 4. Vocabulary

Day 7's plan assigned `domain-modeling` two terms `CONTEXT.md` lacks. Both are
load-bearing for these skills and neither has been written:

- **the dataset's identity within a Run** — the content digest over matrix and label
  codes that binds profiling, planning and execution to the same data. Every skill
  depends on it and none can currently name it.
- **the settings the Battery is computed under** — the `k`, sample cap and seed fixed by
  published rule from the Reference's row count. `CONTEXT.md` lists "protocol" as a word
  to avoid, so that term is not available.

Day 8 adds a third:

- **the re-plan round** — the single bounded post-evaluation opportunity to extend the
  portfolio, now that it can no longer mean re-weighting.

`domain-modeling` settles the final wording. The skills are written after the terms
exist, not before, for the reason day 6 moved `CONTEXT.md` forward in the first place.

## 5. Testing and the end-to-end drive

**The toolbox routes get tests first,** as day 7's tasks did. Specifically:

- `status` across partially complete Runs, including one where the re-plan round is
  spent and one where a Candidate has a failed Outcome with a retry still available.
- `log-decision` refusing a non-resolving key and naming it, accepting an empty
  `evidence`, accepting a key whose value is legitimately null, and recording
  `evidence_resolved` with the value the key held at write time.
- A decision logged against an artefact that is then regenerated with a different value,
  asserting the logged reading and the current reading differ and that both survive —
  the regression that makes day 8b able to detect rebinding.
- `suggest-base` against the fixtures, asserting it agrees with `recon`'s rule rather
  than reimplementing it.
- **Retry accounting:** a third `embed` attempt on one Candidate id is refused; a Run
  interrupted after a failed first attempt still offers the retry on resumption. Day 7's
  lesson was that five of nine fixes reintroduced the class of defect they closed, so
  both directions get a test, not just the one that prompted the change.
- **Budget:** `embed` refuses a `--timeout` above the registered Plan's Budget-derived
  cap, and `_check_reregistration` refuses a changed `Plan.budget`.
- The adapter digest appears in `meta` and on the manifest, and changes when the adapter
  file changes.

**The skills are exercised by use, not by unit test.** Day 13 is where agent-behaviour
tests live. Day 8's check is that the chain runs:

1. Each skill invoked alone against a prepared Run directory, confirming it reads its
   state from files and does not depend on a predecessor having run in the same
   conversation.
2. `/analyze` end-to-end with `--auto` on a synthetic fixture, which is the daily smoke
   test the fixtures were built for.
3. A deliberate failure injected — a Candidate configured to fail — to confirm the
   diagnose-and-retry loop produces the record it is supposed to produce.

Item 3 is not optional. It is the single piece of evidence the design leans on hardest,
and it has never been run end-to-end.

**Stretch, if the fixture drive is clean:** `/analyze` on dataset 1 through to `rank`
and `figures`, stopping short of the report. It would be the first time the chain meets
a real dataset, and it would tell day 8b what the report has to work with.

## 6. Scope

**In:** `status`, `log-decision`, `suggest-base`; giving `Plan.budget` a consumer and a
freeze, and making `embed --timeout` a cap; retry accounting; the adapter digest; the
four skills; `/analyze`; the two assigned `CONTEXT.md` terms plus the re-plan round; the
layout below; the end-to-end drive.

**Layout.** Canonical files in `.claude/skills/<name>/SKILL.md` and
`.claude/commands/analyze.md`, so cloning and opening Claude Code gives the bare
`/analyze` the README promises, with no install step. `.claude-plugin/plugin.json`
declares custom paths into `.claude/`, so the same files install as a plugin without a
second copy. Plugin skills are always namespaced, so installed elsewhere the entry point
is `/dr-agent:analyze`. The README's layout table is wrong today — it shows `skills/`
and `commands/` at the repo root, which is the plugin layout, not what project-level
discovery reads — and this spec corrects it.

**Out, and where it goes:**

| Deferred | To | Why |
|---|---|---|
| `write-report`, report template, pandoc | day 8b | the report is generated from the decision log, and day 8 is what first produces one worth generating from |
| First dataset-1 run *with a report* | day 8b | cannot complete without the above |
| `recon --k` and `--max-samples` | day 9 | assigned by day 7; the agent can still tune its own evidence |
| Nine day-6 review defects, five day-7 inheritances | day 9 | already queued |
| Adapter execution in an isolated subprocess | day 9 | joins the queued Loader defects; returning a sparse matrix across a process boundary has not been scoped |
| Report-time detection of evidence rebinding | day 8b | day 8 records `evidence_resolved`; reading it back is the report generator's job |
| Adapter sandboxing (filesystem, network policy) | not scheduled | declined with reasons in section 3; it would claim containment the surrounding runtime does not provide |
| Amendment | unscheduled | still a defined term with no mechanism; every refusal that would need one says so |
| Plugin distribution, marketplace | day 13 | the manifest lands here, distribution does not |

**Two design commitments this spec changes, for the notes' decision log:**

§3.1's "one optional re-plan is permitted after evaluation" is narrowed by day 7's
freeze to mean extending the portfolio only. Re-weighting and re-baselining are no
longer available within a Run at all, and the honest description is that the re-plan
adds Candidates.

§3.5's hyperparameter sweep is absorbed into that same round rather than being a
separate mechanism, because "add new Candidate ids after evaluation" is precisely what
it is.

**What day 8 does not resolve:** the schedule. Day 8b is a new index, and the cut order
stands — GPLVM first, then the rules-planner hedge, never the tests and never day 14.

## 7. The adversarial review of this spec, and what it changed

The draft went through Codex's adversarial reviewer before any implementation, which is
the same pass day 6 ran against the design and for the same reason: after the skills
exist, a contract change is a rewrite of everything built on them. Four high findings,
all four verified against the code rather than accepted on the reviewer's word. All four
were real. The useful thing is that they were not all the same kind of real.

**One was my error, not a gap.** I proposed a second Budget on the manifest without
checking that `Plan.budget` already existed. It does, it has no consumer anywhere, and
nothing freezes it. The correction removes surface instead of adding it, and the defect
it would have created — two authorities nothing required to agree — is the same shape as
the profile-against-cache divergence day 6 found. The lesson is narrow and repeatable:
grep for the field before designing the field.

**One was made worse by my own wording.** "Embed per Candidate that lacks an Outcome"
would have skipped a failed Candidate on resumption, so an interrupted Run would lose
the retry the design promises — a failure becoming permanent because a process died
rather than because the diagnosis was exhausted. The underlying gap, that nothing counts
attempts, was already there; the phrasing added a second failure mode pointing the
opposite way. Both are closed by counting attempts in `status` and refusing a third in
`embed`.

**One found a guarantee that only holds instantaneously.** Validating an Evidence key at
write time and reading its value at report time are different guarantees unless the log
carries what it saw. Since `recon` can still be re-run with a different `--k` — day 9's
hole — a rationale can be silently rebound to evidence that was never behind it.
Recording `evidence_resolved` is cheap, because validation already resolves the keys and
was throwing the answer away.

**One was right about the mechanism and wrong about the remedy.** Adapter code does
execute unsandboxed before any check, and the module docstring overstates what the
contract buys. But a filesystem-and-network policy around the Loader, underneath a
runtime where the agent already has shell access with the same permissions, contains
nothing while licensing the report to claim containment. Day 8 takes the auditable part
— the adapter's content digest, so the record names the code — narrows the docstring,
and sends subprocess isolation to day 9 unscoped rather than promising it on an estimate
never made. Declining a recommendation is not the same as dismissing the finding, and
the reasoning is recorded here so that a later reader can overrule it knowingly.

Rejected: accepting the sandbox recommendation to close the finding cleanly. Also
rejected: treating "the reviewer verified it against the code" as sufficient — the
Budget finding understated its own severity, and only reading `plan.py` showed why.

### 7.1 What reviewing every task found, and what it says about this spec

The four toolbox tasks were each reviewed on commit rather than at the end. Thirteen
further findings, all verified against the code, none caught by the tests written to
prove those tasks worked. The sections above have been rewritten to match what the code
now does; this records what the pattern was, because it is more useful than the list.

**Every one lived where new code met old behaviour.** Not a wrong line — a correct line
whose surroundings did something the author had not re-derived. A ranking nothing clears
when the portfolio changes. A `RunDir` that makes directories on construction. A
`run_pipeline` that raises past the record meant to count it. A `validate-plan` that
appends a registration record whether or not anything changed. This is day 6's
observation repeating exactly: *178 passing tests coexisted with nine real defects,
because the tests exercise each unit on the shapes it expects, and these live where two
components disagree.*

**Three of the thirteen were caused by fixes for earlier findings in the same run.** The
re-plan round was defined three times before it was right: by position, then by digest,
then by net portfolio growth. Each earlier definition was defensible and each was
silently wrong for a case the next review found. Day 7 recorded that five of nine tasks
had a fix that reintroduced the class of defect it was closing; the rate here is
comparable, and the only reason it did not ship is that something adversarial looked
after each one.

**One was a test that passed when it should have failed.** The regression written to
prove the "a refusal writes nothing" fix compared file contents, and the refused Plan
differed only in its Budget — which does not change the validation report. The file was
rewritten with identical bytes and the assertion saw nothing. A green test proves nothing
unless it has been seen red, and every regression on this branch was checked that way
afterwards.

**The most serious finding was against this document, not the code.** Nothing in the
first draft's `log-decision` section considered that a general write route into the
decision log could forge the records day 7's freeze reads as evidence. The spec described
evidence-key validation and stopped there. The code did what the spec said, and the spec
was incomplete in a way that would have undone the previous day's work. Section 2 now
carries the rule.

The lesson for the remaining tasks, and for day 8b: the question to ask of new surface is
not "is this correct" but "what already reads what this writes".
